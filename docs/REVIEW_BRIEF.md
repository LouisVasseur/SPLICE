## 1. Problem setting

**Goal.** A learned index for sorted 64-bit integer keys with 8-byte payloads that is faster than the state of the art at a fixed,
small memory budget, first for point lookups (done earlier) and now under writes: payload updates, deletes and inserts. The design
has three named parts, T (transform: a directory), G (gap compression) and V (virtual positions: spare slots and fitted lines), and
the claim under review is that **each of the three is a useful design decision in a write setting, and that together they make a
novel learned index design**.

**Benchmark.** GRE (Wongkham et al., "Are updatable learned indexes ready?", PVLDB 2022), its `microbench` driver, unmodified apart
from added index names. One thread. A run bulk-loads keys, then executes 100M operations and reports throughput (operations / s)
and the index's own `memory_consumption()`. Operation streams are generated by GRE's driver (`src/benchmark/benchmark.h`):
- reads sample uniformly from the bulk-loaded keys only (never from inserted keys);
- inserts take the keys of the file not bulk-loaded, in file order (`init_table_ratio` = 0.5 for insert mixes: 100M bulk, the rest
  inserted);
- updates sample from the bulk-loaded keys;
- deletes take keys from a separate pool, the second half of the key array (`del_table_ratio` 0.5), so reads may hit deleted keys.

Mixes used (`/scratch/lvasseur/write/wcell.sh`): `read` (100% reads), `upd50` (50/50 read/update), `upd100`, `del50` (50/50
read/delete), `ins50` (50/50 read/insert, init 50%), `ins5` (95/5, init 50%).

**Metric and budget.** Throughput at a memory budget. SPLICE is built at **20 bytes per key** for read/update/delete (8-byte key +
8-byte payload = 16 bytes, so 1.25 slots per key at most, minus directory), **30 B/key** at the start of `ins50` (100M bulk keys
must leave room for 50M inserts) and **21 B/key** for `ins5`. Each baseline runs at its own memory (and, since 2026-11-23, at its
best setting; see 7.2). The cost model of the design is **cache lines read per lookup**: a 64-byte line holds B = 4 pairs.

**Hardware and hygiene.** Jed (EPFL SCITAS), Intel Xeon Platinum 8360Y (Ice Lake, 2.4 GHz), whole node per batch job, four pinned
lanes on cores 2, 20, 38, 56 (one per NUMA domain) running one cell each, 4 KiB pages (transparent huge pages off via
`/scratch/lvasseur/bin/nothp`), GCC 11, `-O3 -march=native`. Earlier passes showed a median spread of 1.0% between passes on the same
node. Comparisons are meant to be within one job (one node); where they are not, the text says so.

## 3. The index

Main code: `include/gret/adaptiveline.h` (`AdaptiveLineIndex<K, P, B, Coord, W>`; `ab4` = B 4, identity coordinate, read-only).
Supporting: `exceptions.h` (outer G), `fastrule.h` (inner G), `gatedg.h` + `discover.h` (the gate), `overflow.h` (writes),
`registry.h` (names). Index names accept `name@VAR=v:VAR=v` to set its environment.

### 3.1 Layout (shared by all parts)
- A single array of 16-byte (key, payload) **slots**, 4 per 64-byte line ("bucket"), sorted by key.
- **An empty slot holds a copy of the next pair** (the last key's copies fill the trailing slots). So the slots stay sorted, a run
  of equal keys is one key and its free copies, and free space is never a special value.
- A key's **bucket** comes from the directory (T) applied to its coordinate (G); the key sits in the first free slot at or after the
  start of its bucket, after the keys before it (`place(p, prev)`), so it can be pushed past its bucket by a backlog.
- `d_`: the build's exact maximum number of lines a stored key sits past its bucket.

### 3.2 Lookup (`get`: 119 x86 instructions for `ab4` under GCC 11)
1. (G) If the raw key is outside the bulk's range: binary search in the far-key array (and, for the writable index, the overflow).
2. (G) v = coordinate(key) - lo (identity: v = key - lo).
3. (T) Walk the directory: root cell = v >> shift, then at most AR_DEPTH child levels, one branch per level; the leaf gives a first
   slot a and a slope c; bucket = (a + floor(frac(v) x c)) / 4.
4. Read the bucket's line; count the keys < x without branching (4 compares). If fewer than 4: the first key >= x decides (hit or
   exact miss). Otherwise read the next line, at most d_ lines on.

The authors treat `ab4`'s `get` as frozen: after every change its disassembly is compared with a reference binary
(`/scratch/lvasseur/gre-gap/GRE/build/microbench.base`), and new members go at the end of the class so offsets do not move.

### 3.3 T: the directory (`build_tree`, `make_node`)
- Root: 2^bits equal-width cells on the top bits of v, bits = min(RADIX_BITS = 16, log2(m / 8), bits of the span).
- A node first skips the key bits all its keys share (`AB_NOSKIP=1` disables, for ablation).
- A node **splits** into 2^k equal-width children when it holds more than AR_LEAF keys, depth < AR_DEPTH (default 3), and its keys,
  placed alone in its buckets, would read more than AR_TAU x (keys) lines in total (exact count, `lines_on`). k = ceil(log2(keys /
  AR_LEAF)), at most AR_KMAX (8). Otherwise it is a leaf: a straight line from rank to slot over its range.
- Node = 8 bytes. The split rule is a line count, not a rank error (the difference from PLEX/RadixSpline-style directories).
- Root cells only (no split, no skip, no far keys): the ablation baseline "root cells only" (`AR_DEPTH=0:AB_NOSKIP=1`).

### 3.4 G: gap compression
Two independent mechanisms, both "remove empty key space so T and V spend nothing on it".

**Outer G, far keys aside** (`exceptions.h: peel_outliers`, `TRANSFORM_G_E`, default 64): while the full span is more than twice
the span without E keys at each end, take one key off whichever end has the larger gap to its neighbour, at most E per end. The
taken keys go to a sorted side array (`exc_`). Only fb has any (21).

**Inner G, the period rule** (`fastrule.h: FastPeriodRule`; index `gp4` = AdaptiveLineIndex over it):
- A rule = room S and blocks {first key f, period P}. For a key x in block c: q = row = (x - f) div P, r = offset = (x - f) mod P,
  and y = base(c) + q (S + P) + floor(S F(r)) + r, where F is the empirical distribution of offsets within a row (tables indexed
  by r's octave).
- With S much larger than P (genome and rows: S = 2^26, P ~ 10^5), each row's coordinate width is spent almost entirely where
  F rises, i.e. where keys are: the empty part of a row shrinks to a relative width of about P / (S + P). y is strictly increasing in
  x within the rule's range; the build checks this and refuses a rule that breaks it.
- F is computed from the stored keys at build time, tabulated per octave of r and linear between knots. Because the r term is
  always there, y is strictly increasing for every key in the rule's range, stored or not, which is what lets inserts use it.
- Cost: `gp4`'s compiled `get` is 217 instructions under GCC against `ab4`'s 119; in GRE the rule adds about 14-27 ns per lookup
  (measured on layouts the rule leaves unchanged, S = 0).
- The rule is found by `discover.h: discover_rule` (FFT over key windows, coherence, refinement, run merging, harmonic check, block
  boundaries, S, row phases; deterministic; 2 s, or 16-25 s when candidate periods appear), on the stored keys.

**The gate** (`gatedg.h: GatedGIndex`, name `sg4`) chooses G at build time: it builds every admissible candidate in full at the same
budget (identity; the discovered rule; bit-field compaction by PEXT when some bits never vary) and predicts each one's lookup time
from its own exact counts:
ns = base + c + f x base, base = A + B (lines - 1) + C (levels - 1), with A, B, C frozen selector weights and the rule's
c = GATE_RULE_NS = 10.24, f = GATE_RULE_F = 0.104. It keeps the cheapest. Dispatch to the kept candidate costs +3 instructions
and +1 branch per lookup, measured 3-8% in GRE. Among the ten datasets it keeps a rule only on genome (and on synthetic rows).

### 3.5 V: virtual positions
- **Spare room.** Slots are assigned in proportion to rank: each key gets the same share, spk = slots per key (the budget's
  remainder after directory and far keys, at 20 B/key about 1.2-1.25). `HASHLINE_SPK` sets spk directly when `AB_BUDGET=0`.
- **Fitted lines** (`fit_lines`, `AB_V=1`): leaf by leaf in key order, behind the real backlog, try other lines for the leaf: the
  rank line and a key-fit line (through the leaf's first and last key), each shifted by 0-3 slots and scaled by 0.9 / 1 / 1.1. Keep
  a candidate only if the lines its keys read plus the next leaf's read go down, no key of the leaf reads more than its worst under
  the rank line, and the leaf ends no later. So the mean, the worst key and the bytes can only stay or improve. No extra metadata:
  the leaf's (a, c) holds the result.

## 4. How the parts are chosen together

There is no gradient-based learning. The parts are chosen by a build-time search whose decisions are coupled; "learned" means fitted
to the keys by exact counts of cache lines.

```
bulk_load(keys, budget):
  G outer: peel far keys (peel_outliers)                                 -> exc_, bulk range
  G inner: coordinate y = rule(x) (gp4: $RULE_FILE; sg4: discovered)     -> y for every bulk key
  repeat (at most ~6 rounds, until spk changes by < 0.001):              # T and V's room share the budget
     spk = (budget x n - far keys x 16 - rule bytes - nodes x 8) / 16 / m
     T: build_tree(cells, spk)   # split decisions use exact line counts with V's rank layout at this spk
  V: fit_lines()                 # per leaf, in key order, given T's leaves and the real backlog
  place every key; d_ = worst displacement; E[lines] = exact mean
sg4 (the gate): do all of the above once per G candidate, predict ns from each one's (lines, levels, rule cost), keep the best
```

So: T's splits depend on V's slots per key (the budget loop), V's fit is evaluated inside T's leaves, and G is chosen by building T
and V on each candidate coordinate and comparing the results. The coupling is real but sequential: no step revisits an earlier one
except the T / room loop, and the gate's comparison is over a handful of discrete candidates.

## 5. Writes

Writable index: `aw4` = `AdaptiveLineIndex<..., IdentityCoord, true>`; `gw4` = the same over the period rule (added 2026-11-23).
Updates and deletes also work on the read-only `ab4`. The read path is unchanged by all of this (the 119-instruction check).

- **update**: the lookup's own loop, then one store into the slot just read. Copies before it keep the old payload (no lookup reads
  them; a scan takes a key's payload from its last copy); copies after it are rewritten only once a key was removed or for the last
  key.
- **remove**: find the key's run of copies; overwrite it with copies of the next pair (of the previous pair for the last key), which
  is how the build writes empty space. Nothing else moves; d_ stays a valid bound. `AB_DEL` selects what is prefetched (no effect).
- **put** (`AW_PUT=line`, default), designed from the loss in cache lines: a key in the overflow costs about 1.0-1.5 lines on its own
  later lookups; a shift across a line boundary costs one line for every key it carries across, forever. So: walk as get; if the
  key's place is inside a line that has a free copy, shift within that line (no other lookup changes); else if the line's last slot
  is free (next line starts with the same key) and reach allows, take it; else the **overflow table**. Keys whose place is before
  their bucket go through `put_general` (gallop search, shifts of at most 8 slots, each moved key checked against its reach).
  Options measured: `AW_PUT=line2` (take a free slot in the next line, +2%), `AW_BACK=1` (+1%), `AW_PUT=wide` (older rule).
- **overflow table** (`overflow.h`): open addressing, linear probing on mix64 scaled by multiply, 16-byte pairs, backward-shift
  erase; sparse by default (doubles at 5/8 full: puts 12-15% faster than the dense variant). A per-line bit records that a key of
  this line went to the overflow, so a lookup that misses in the slots asks the table only then (`AW_OVBIT=0` disables). The
  overflow table is **not G**.
- **rebuilds** (off by default, `AW_RW` = expected reads per write): rent-or-buy. Debt accumulates as (reads per write) x (overflow
  share) x 60 ns per put; when it reaches the measured build cost of the whole index, rebuild everything at the same budget, or
  per root cell when a cell is "hot" (`AW_HOT`). Variants: lay a cell out again inside its own slots (`AW_INPLACE`), merge the
  overflow cell by cell, a bounded share per put (`AW_ROT=1`), with three tables in rotation (`AW_ROT=3`, the TA's "three ring
  buffers" idea), bounded extra slots for moved cells (`AW_ARENA`, default 0.1 of the slots). Rebuilds are off under the rule
  (`gw4`).

## 6. Testing and measurement modules

**Correctness.**
- `tests/test_put.cpp`: 540 cases (key sets: single leaves, deep directories, spills, empty cells, far keys, keys 0 and 2^64 - 1,
  huge gaps; 3 leaf sizes x AB_V x budget 0 / 40 x 3 put orders): after every batch of puts, updates, removes, every key ever stored
  and its neighbours and random keys are looked up, and scans from many start keys are compared with a `std::map`. `TEST_INDEX`
  selects the index (aw4, gw4, ...). Run in every write mode (line, line2, back, wide, rebuild and merge modes).
- `tests/test_write.cpp` (update/remove on ab4, same style), `tests/test_scan.cpp`, `tests/test_index.cpp`, `tests/sota/test_*.cpp`
  (one per added baseline, against a sorted reference).
- In every timed run GRE's success counters must match, and the timed tool checks every key's payload (exit 1 on any wrong answer).
- No mutation testing has been done.

**Timing.**
- GRE `microbench` (`/scratch/lvasseur/gre-gap/GRE/build/microbench.v8`; baselines in `build_all/microbench.all`), run by
  `/scratch/lvasseur/write/lanes_t.py OUTDIR CELLS` (four pinned lanes, 45-minute timeout per cell, results in OUTDIR/cells.tsv and
  logs/).
- `tools/corrupt/regret.cpp`: bulk-load on the base keys, time a stream of puts (holdout = same distribution, hot = one range,
  append), then time lookups over all keys, the base keys and the **inserted** keys (which GRE never reads), and a fresh build of the
  same keys at the same bytes: regret = in-place / fresh. `AW_G=1` runs gw4/gp4. `PUT_LAT=1` times every put (p99, p99.9, max).
- `tools/corrupt/sim.cpp`: a counts-only simulator of the layout under write streams (lines read, overflow, KS/TV distances of the
  changed CDF), validated against real get/scan; used to design the put rule and rebuild policies.

**Analysis.** `/scratch/lvasseur/write/tab16.py` (T/G/V ladder), `tab17.py` (per-operation trials), `tab20.py` (G on/off),
`scripts/plot_write_ladder.py` (figures F62-F65 in the meeting-5 style). Write-aware cost model: `~/Downloads/GRE-gate-wf/tools/gate/
{collect.py, fit.py, povest.cpp}`, results in `~/Downloads/GRE-transform/results/gatewf_2026-11-23/model/fit.txt`.

## 7. Results so far (200M keys, Jed, one thread)

### 7.1 Read-only (SPLICE at 20 B/key)
Ahead of 22 other indexes and searches (B+tree, ART, PGM, ALEX, LIPP, RMI, CHT, RadixSpline, PLEX, DILI, FAST, PGM++, CSV, AFLI,
SALI, DyTIS, BLI, NFL hybrid, binary / radix binary / interpolation / three-point search), each at its best setting, by **1.04x (fb,

### 7.4 Mechanisms per operation (batch17, nine datasets, one pass)
- Update = lookup + one store; the store costs 9% (median; `AB_UPD_DRY=1` skips it); without it 0.96-0.99 of read speed.
- Delete: every index loses a similar share of its own read speed in GRE's 50% delete mix (SPLICE 0.73, LIPP 0.74, AFLI 0.73,
  ALEX 0.79), so the delete lead comes from the read side. Prefetching neighbours: no effect.
- Insert = lookup + 110-190 ns of writing. The overflow share does not set insert throughput in GRE's mix: doubling the spare room
  (22 to 44 B/key) cut fb's overflow 76% to 40% at the same speed (batch16 sweep).
- Write-aware cost model (fit.txt): predicts every GRE cell with a median error of 0.8% (read), 1.4% (updates), 2.1% (deletes),
  2.5% (inserts); store = 4.4 ns + 0.10 L, delete write = 29.9 + 0.33 L, put = 132.6 + 0.82 L (L = lookup ns); an overflowed key
  costs 64 ns on every later lookup of it; the build can estimate the overflow share of future same-distribution inserts within 4.3
  points (median) from its own keys.

### 7.5 After inserts (regret13/15/17/20, 20% more keys, timed tool)
- 60-82% of inserted keys end in the overflow; lookups afterwards are 8-28% slower than a fresh build (median regret 1.08 same
  distribution, 1.28 hot range); lookups of the new keys about 95-170 ns vs 50-130 for all keys.
- Rebuilds remove the regret but stall: a full rebuild makes one put wait 18-47 s. The cell-by-cell merge with room for 50% more
  slots (`AW_ARENA=0.5`) needs no full rebuild on hot-range inserts (longest put 0.10 s) at 26.6 vs 20.2 B/key; with 10% room every
  dataset still stalls once. Three tables in rotation gain nothing over one on one thread.
- G under inserts (genome, same distribution, regret20, one pass): puts 322 to 268 ns, overflow 79% to 63%, lookups of all keys 131
  to 99 ns, of new keys 173 to 154 ns. The workflow's rules stage repeated it with per-put clocks, three passes: puts x1.23,
  lookups of all keys x1.33, of new keys x1.12 (`/scratch/lvasseur/gatewf/rules/tab_rules.txt`).

## 9. Review questions (what the authors think is weakest)

1. **Attribution.** The ladder is order-dependent (T first). Is a fair attribution (all orders, or Shapley over the 2^3 settings)
   needed before claiming each part matters? The G x V grid covers part of this.
2. **Is "learned" justified?** Section 4: decisions are exact-count searches over a few discrete choices per node or candidate,
   coupled sequentially. Is the joint-optimisation claim stronger than the code supports?
3. **G's applicability.** The inner rule exists on one real dataset of ten; rows was built to have one. Outer G matters on one (fb).
   Is G a general design decision or a dataset-specific trick? What would a more general gap compression look like?
4. **V's write role.** Spare room spread evenly by rank; on bunched data half the new keys overflow even with twice the room. Is
   the design missing a write-aware V?
5. **Benchmark validity.** GRE's insert mix never reads inserted keys, so overflowed keys cost nothing there; deletes come from a
   separate pool; one thread; uniform reads. Do the write conclusions survive YCSB-style or skewed reads of new keys?
6. **Fairness.** Mixed nodes for some baseline bars; one pass for the new baselines; `memory_consumption()` is each index's own
   definition (GRE's B+tree wrapper reports 0); best-setting sweeps were complete only for read-only and partly for writes
   (BLI at bli20 changed three cells). DyTIS is incomplete (builds of 4.6-7.3 hours at 200M).
7. **Invariants.** The 119-instruction `get` and "new members last" rules: do any write-path members change `get`'s code for `ab4`
   (they should not; checked by disassembly), and does `gw4`'s out-of-range path change `gp4`'s `get` (checked identical)?
8. **Rebuild policy.** The 60 ns per overflow lookup in the debt and the rebuild cost are measured constants; is rent-or-buy the
   right frame when the stall itself (18-47 s for one put) is unacceptable for many uses?
9. **Losses.** BLI at 50% inserts on fb, osm, planet; LIPP on stack. Is the explanation (put = lookup + shift or hash insert;
   BLI's unsorted buckets need neither) right, and is there a design answer inside T/G/V?
10. **Testing gaps.** No mutation testing; tiny key sets refused at 40 B/key for gw4 (126 of 540 cases); real-rule correctness
    checked only at 200M through GRE counters and the timed tool.
